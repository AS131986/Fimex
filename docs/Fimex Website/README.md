## Текущая реализация и границы

- Общий вход отправляется в `POST api/auth`. Сервер ищет email пользователей gate admin/provider и выдаёт dashboard admin либо supplier. Админ перенаправляется в legacy admin, поставщик — в `/dashboard/supplier/statistic`.
- Вход содержит ограничение 5 попыток на ключ email+IP с периодом 120 секунд; границу и фактический отсчёт нужно проверить на стенде.
- Восстановление использует `api/auth/forgot/send-code`, `check-code`, `api/auth/reset/{token}`. Отправка повторного письма ограничена минутой, код состоит из четырёх символов и проверяется в окне двух минут; токен сброса в конфигурации действует 60 минут. Не смешивать три разных срока.
- В обычном восстановлении сервер выбирает активного provider. Это не доказывает проверку статуса родительского поставщика. Для сотрудников и клиентов этот обработчик восстановления не предусмотрен; возможность их восстановления через публичную форму требует WEB-Q04.
- Приглашение менеджера с email/token и modal=#reset-modal вызывает `confirm-email`, затем автоматический вход. Обычный сброс возвращает к форме входа.
- Заявка передаёт company, email, phone, brands, market_duration, avg_turnover. Сервер отправляет письмо на настроенного получателя, в текущем снимке — suppliers@fimex.ae. Положительные проверки выполнять только с перенаправлением доставки в тестовый почтовый приёмник. Самостоятельного создания поставщика в этом обработчике нет.

## Расхождения для приоритетной проверки

1. Схема `authValidationSchema` объявлена, но в `LoginForm` не подключена к Formik. Сервер входа проверяет обязательные строки, не формат email. Проверить невалидный ввод через Enter и прямой запрос.
2. Для нового пароля схема формы задаёт min(6), подсказки — 8 символов, верхний/нижний регистры и цифру; reset на сервере требует 8 и смешанный регистр/цифру. Подтверждение приглашения проверяет 8 и совпадение, без тех же требований к составу. Enter вызывает отправку через Formik независимо от видимости кнопки.
3. Обработчик входа сам явно не фильтрует status; `SoftDeletes` у User не доказывает каскадный запрет менеджерам архивного поставщика. Проверять и выдачу токена, и дальнейшие API, не утверждать обход до прогона.
4. Код ввода OTP принимает последний введённый символ без фильтра цифр; вставка может сохранить остаток прежнего кода. На отказ Resend UI также ставит минутный отсчёт; проверить понятность результата.
5. Ошибка сохранения пароля помещается в поле password, а форма показывает список невыполненных требований. Проверить видимость серверного отказа при формально правильном пароле. Вход без текстового сообщения ошибки также может не показать причину.
6. В заявке нормализуются название/бренды, телефон фильтруется и ограничивается 20 символами. Регэксп телефона допускает скобки/плюс без цифр. UI ограничивает company/brands до 100 и email до 254; сервер задаёт company/email 255, phone 50, без аналогичных верхних пределов остальных строк и перечислений селектов.
7. В заявке показаны только ошибки email/phone, а серверная ошибка записывается в email независимо от поля. Проверить видимость ошибок остальных полей, доступность повтора и отсутствие ложного успеха при сбое почты.
8. HomeEntry использует token/dashboard из хранилища для перенаправления, а вход через authorize не сохраняет dashboard. Проверить обновление главной, ошибочные значения и переходы после служебного входа. Любая ошибка getMe очищает сессию — проверить временные сетевые сбои отдельно от 401.

## Открытые вопросы

- **WEB-Q01 — идентификаторы.** Поддерживается ли вход поставщика/сотрудника чем-либо кроме email; регистр, trim и коллизии между типами. Для запрещённых клиентских типов отказ требуется при любом из указанных пользователем идентификаторов.
- **WEB-Q02 — статусы пользователей.** Перечень и семантика собственных статусов менеджера/сотрудника, исключения супер-админа. Запрет по неактивному/заблокированному/архивному родителю не зависит от этого вопроса.
- **WEB-Q03 — жизненный цикл сессий.** Одновременные входы, вкладки, отзыв других сессий при выходе/смене пароля/восстановлении. Обязательное прекращение доступа после блокировки, деактивации и архивации уже согласовано.
- **WEB-Q04 — восстановление запрещённых аккаунтов.** Допустимость отправки кода и изменения пароля без предоставления доступа для неактивных/заблокированных/архивных пользователей; восстановление сотрудника через эту форму. Ни сброс, ни приглашение не должны активировать архивного поставщика или обходить запрет входа.
- **WEB-Q05 — коды и токены.** Лимит неверных OTP, валидность старого кода после Resend, повторная выдача токенов, границы сроков и отзыв предыдущих токенов. Времена из кода требуют проверки конфигурации стенда.
- **WEB-Q06 — единая политика пароля.** Устранение различий схемы, подсказок, reset и confirm-email; максимальная длина, Unicode, пробелы и повтор прежнего пароля. Не устанавливать дополнительные ограничения без согласования.
- **WEB-Q07 — валидация заявки.** Единые пределы UI/сервера, формат и минимальная длина телефона, допустимые значения селектов, сообщения всех полей. Не превращать слабую серверную проверку в требование принимать некорректные значения.
- **WEB-Q08 — повторные заявки.** Допустимость повторной заявки на существующий/архивный email, частота и дубли писем. Заявка не восстанавливает и не меняет аккаунт.

Полное покрытие по имеющемуся коду не означает закрытие перечисленных вопросов. Проверки помечаются выполненными только после фактического прогона; зависимые от архива, прав и почты остаются невыполненными до готовности стенда.
