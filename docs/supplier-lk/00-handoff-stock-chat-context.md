## 2. Цель текущей ветки работы
Оформить документацию по странице `Stock` в контуре `Supplier LK` и хранить её в `docs/supplier-lk/...`.

Главная практическая цель:
- держать компактную и прикладную документацию по странице;
- иметь **сценарный checklist** для прогона;
- избегать расплывчатых формулировок и дублей кейсов;
- не потерять критичную бизнес-логику по `Price`, `rank`, `move`, `duplicates`, Buyer/Admin consistency.

## 3. Как работать в новом чате

### 3.1. Стиль ответов
- Отвечать **на русском**.
- Работать как **Senior QA Engineer / QA Analyst**.
- Не выдумывать требования.
- Если факт не подтвержден — явно помечать как:
  - предположение;
  - open question;
  - риск.
- Фокусироваться на:
  - negative scenarios;
  - edge cases;
  - boundary values;
  - concurrency / race conditions;
  - stale state;
  - роли и доступы;
  - интеграции;
  - консистентность данных;
  - regression impact.

### 3.2. Как писать checklist
Нужен **компактный сценарный формат**.

Правильный стиль кейса:
- `Товар A ...` → `ожидаемый результат`

Что важно:
- без длинных абстрактных формулировок `Проверить, что...`;
- без воды;
- без лишних `Предусловие / Действие / Ожидаемый результат`, если можно сказать короче;
- без кейсов, где тестировщик должен сам додумывать, что проверять;
- без описания flow, которого нет в UI;
- одинаковые ожидаемые результаты по возможности объединять;
- но при этом **не терять покрытие реальной логики**.

### 3.3. Что особенно важно для пользователя
Пользователь очень чувствителен к:
- дублирующимся кейсам;
- непонятным формулировкам;
- избыточным формулировкам;
- пропуску реальной бизнес-логики;
- слабому покрытию блоков:
  - `Price`;
  - `rank`;
  - `move`;
  - `duplicates`.

## 6. Важные факты по логике Stock

### 6.1. Add Stock / даты
- На странице есть вкладки по датам и вкладка `ALL`.
- Дату добавления можно сменить уже **в окне выбора товара**.
- Доступность даты зависит от КТ, `admin holiday`, `supplier holiday`.
- После КТ / holiday дата может стать недоступной даже при открытой форме.

### 6.2. Товар без `Price`
Если у товара есть `Q-ty`, но нет `Price`, то он:
- виден в `Supplier Stock`;
- не появляется в продаже;
- не появляется в `Admin Stock`.

После установки `Price` товар:
- появляется в продаже;
- появляется в `Admin Stock`.

После удаления `Price` товар:
- остается в `Supplier Stock`;
- исчезает из продажи;
- исчезает из `Admin Stock`.

### 6.3. Add Stock / уже добавленный товар
Если товар уже есть на выбранной дате:
- его `Q-ty` может отображаться в `Add Stock`;
- если у пользователя есть право редактирования, `Q-ty` можно менять прямо там;
- `manager limited` не может редактировать чужую запись;
- количество чужой записи может отображаться.

### 6.4. Роли
- `admin` — может видеть и редактировать все товары.
- `manager full` — может видеть и редактировать все товары поставщика.
- `manager limited`:
  - видит только свои записи в stock list;
  - может добавлять любой товар, доступный поставщику;
  - ограничение не по ассортименту;
  - ограничение в том, что он не может добавить товар на выбранную дату, если этот товар уже добавил другой участник команды;
  - в `Add Stock` может видеть количество чужой записи на той же дате;
  - не может редактировать чужую запись.

### 6.5. Price / rank / hover
- Если `Price` занят в конкурентной группе, срабатывает auto-increment до ближайшего свободного значения.
- При auto-increment отображается **тост** о том, что выбранная цена занята.
- Нужно покрывать не только единично занятую цену, но и цепочки занятых цен.
- Обязательный кейс: **повторно поставить ту же самую цену, которая уже стоит у этой записи**.
  - Не должно вызывать self-conflict.
  - Не должно вызывать лишний auto-increment.
  - Не должно менять `rank`, если фактическая цена не изменилась.
  - Не должно создавать дубли или ложные обновления.
  - Не должно сбрасывать синхронизацию с Buyer app и `Admin Stock`.
- Если `rank` равен `№1` — hover на `Price` **не отображается** (нет лучшей цены для показа).
- Если `rank` не `№1` — при hover на `Price` показывается **лучшая цена по товару**.

### 6.6. Move / auto-move
Нужно покрывать:
- manual move;
- auto-move после КТ;
- auto-move после `admin holiday`;
- auto-move после `supplier holiday`.

Важно:
- логика конкуренции цен и видимости после auto-move должна совпадать с manual move;
- нужен кейс: одинаковый товар на `16` и `17` у одного поставщика → после переноса с `16` на `17` остается товар с **меньшей ценой**;
- нужны сценарии конкуренции и со своим товаром на другой дате, и с товарами конкурентов;
- visibility (дальняя/ближняя дата) при manual move и auto-move тестируется одними кейсами — результат одинаков.

### 6.7. Дубли
Одна из самых важных зон.

Нужно явно контролировать отсутствие некорректных дублей:
- после add;
- после edit `Price`;
- после edit `Q-ty`;
- после повторной установки той же цены;
- после manual move;
- после auto-move;
- при cross-date competition;
- во вкладке `ALL` (особенно после auto-move);
- в `Admin Stock`;
- в Buyer app.

### 6.8. Заказы
После изменения `Price` нужно проверять сохранение цены в:
- заказе клиента;
- заказе поставщика;
- заказе админа.

Все три покрыты: заказ поставщика и заказ админа — в блоке 6.1 checklist, заказ клиента — в блоке 6.2.

### 6.9. Buyer app / Best offer / Top 3
- Если товар присутствует на ближней и дальней дате, и **ближняя дата дороже** — в Buyer app видны **оба** оффера.
- Покупатель может купить по цене ближней даты, даже если она не является лучшей в группе.
- Это подтверждённое бизнес-правило, не open question.

## 7. Что нельзя писать / что обязательно учитывать

### 7.1. Нельзя писать
- нельзя придумывать отдельный `Save`, если товар сохраняется сразу после ввода / выхода из поля / `Enter`;
- нельзя писать flow, которого нет в UI;
- нельзя писать, что товар виден только во вкладке своей даты без оговорки про `ALL`.

### 7.2. Обязательно учитывать
- сортировка в stock list должна соответствовать порядку, настроенному в **номенклатуре**;
- проверки товара без `Price` должны быть прикладными и короткими;
- конкурентная логика должна проверяться и для своего товара на другой дате, и для товаров других поставщиков.

**Итерация 2** — точечная чистка блоков `2.2 Price`, `2.3 Move`, `3.3 Rank`, `3.4 Duplicates`, `6.1–6.4`:

- `2.3`: убраны 4 дублирующих кейса видимости → заменены 2 компактными; удалён кейс stale-state после auto-move (дубль 2.5/4.3).
- `3.3`: разделён кейс «конкурент снижает / удаляет»; удалены два дубля с 2.2 и 5.2; добавлен негативный кейс hover у rank №1.

- `6.1`: заказ поставщика добавлен явно.
- `6.3`: кейс «купить не по лучшей цене» переформулирован под конкретный сценарий ближней/дальней даты.
- `6.4`: переформулирован кейс «скрытый товар»; добавлен кейс синхронизации контуров при повторной установке той же цены.

**Итерация 3** — чистка дублей между разделами и исправление размытых формулировок:
- `5.2`: удалены два дубля с `2.2` — «повторно установить текущую цену» и «цепочка занятых цен».
- `5.5`: удалён дубль с `2.3` — «сохраняется меньшая цена при move».
- `1.3`: формулировка «отображается в связанных местах UI по правилам видимости» → конкретная: «сохраняется в `Supplier Stock`; если есть `Price` — обновляется и в `Admin Stock`».
- `5.5`: формулировка «обрабатывается по бизнес-правилу» для Q-ty при merge → явная пометка `⚠️ Open question`.

### Текущий статус
Checklist **финально вычищен** по всем приоритетным блокам. Активных дублей нет.

## 9. Open questions (актуальные)

- **Q-ty при merge после move**: если два одинаковых товара одного поставщика сливаются на целевой дате после переноса — какое итоговое `Q-ty`? Бизнес-правило не зафиксировано. Помечено в `5.5` checklist.
- **Сбой auto-move**: что происходит, если auto-move не сработал по техническим причинам? Видит ли поставщик ошибку? Остаётся ли товар на старой дате? — риск, не покрыт в checklist.
- **Дробный Price**: поддерживает ли система дробные значения цены (например, `0.01`)? Граничное значение не покрыто в блоке `8.2`.
- **Top 3 в Buyer app**: наличие экрана `Top 3 price ranking` при покупке — факт не подтверждён. Кейс в `6.3` checklist помечен как условный.
