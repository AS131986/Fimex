# Главная, авторизация и заявка поставщика — чек-лист

Основание: локальные снимки `new-fimex-main` и `fimex-back-master`, проверенные 17.11.2026; требования пользователя и [правила поставщиков](../Fimex%20Admin/Suppliers/README.md). Сводка источников и открытых вопросов — [README](README.md).

Все пункты ожидают выполнения. Это подготовка проверок по коду; функциональный прогон не выполнялся. Исследовательский результат не отмечать успешным до согласования правила. На стенде фиксировать сборку фронта/сервера, дату, браузер, ID пользователя и поставщика, предусловия, фактический результат и дефект. Не сохранять пароли/токены в отчётах.

## Подготовка и матрица пользователей

- Использовать тестовый стенд и тестовый почтовый приёмник; письма реальным адресатам не отправлять. Подготовить доступ к логам, сообщениям и тестовому управлению статусами, архивом, часами и отказами сети.
- P1: админ и два менеджера с разными email/паролями. P2: контрольный активный поставщик. Для каждого запрета проверить основного админа и каждого менеджера, UI и прямой запрос. Открытые сессии держать в разных профилях браузера.
- Подготовить обычного клиента, корпоративного клиента и перекупщика; для каждого — отдельные email и клиентский логин/номер, правильный пароль, дополнительные аккаунты при наличии. Правильный пароль обязателен, иначе тест не доказывает проверку типа пользователя.
- Позитивные почтовые тесты выполнять с реально контролируемыми email. Пограничные длинные адреса проверять по валидации отдельно от доставки.
- Состояния поставщика и пользователя изменять независимо; статус архивной записи может оставаться «Активен». Проверка запрета входа по форме не заменяется служебным входом за пользователя.

| Контур / состояние | Проверяемые аккаунты | Ожидание |
| --- | --- | --- |
| Активный сотрудник | Супер-админ, сотрудник с ограниченными правами | Своя админка с назначенными правами |
| Активный поставщик | Основной админ и каждый активный менеджер | Свой кабинет и своя роль |
| Неактивный / заблокированный поставщик | Админ и менеджеры, включая индивидуально активного | Новый вход запрещён, старые сессии теряют доступ |
| Архив при любом сохранённом статусе | Админ и все менеджеры | Вход и действия по старым сессиям запрещены |
| Удалённый менеджер | Старые email, пароль, токен | Доступ запрещён |
| Восстановленный поставщик | Каждый фактически восстановленный пользователь | По итоговому статусу; состав восстановления требует SUP-Q11 |
| Обычный / корпоративный клиент / перекупщик | Каждый тип по логину и отдельно по email; дополнительные аккаунты | Нет входа в админку и кабинет поставщика |
| Неизвестный пользователь / неверный пароль | Каждый разрешённый тип как контроль | Отказ без рабочей сессии |

Для запрещённых типов повторять попытку при чистом браузере и при существующем токене этого типа. Проверять не только переход, но и фактический доступ к защищённому API. При невозможности создать состояние отмечать блокировку с причиной, а не успешное выполнение.

## 3. Авторизация и типы пользователей

- [ ] **WEB-LOGIN-01 — Вход сотрудника админки**

  <details>
  <summary>Подробности проверки</summary>

  - В чистом профиле войти корректными email и паролем активного сотрудника; повторить для супер-админа и сотрудника с ограниченными правами.
  - Ответ dashboard=admin ведёт в административный интерфейс через /oauth/authorize; подтверждены ID пользователя и его права. Кабинет поставщика не открывается вместо админки.

  </details>

- [ ] **WEB-LOGIN-02 — Вход админа поставщика**

  <details>
  <summary>Подробности проверки</summary>

  - Войти email и паролем основного пользователя активного неархивного поставщика P1.
  - Открывается кабинет P1, текущая начальная страница — /dashboard/supplier/statistic; профиль и данные принадлежат P1, административные права сотрудника не выдаются.

  </details>

- [ ] **WEB-LOGIN-03 — Вход менеджеров поставщика**

  <details>
  <summary>Подробности проверки</summary>

  - Поочерёдно войти двумя активными менеджерами P1 и менеджером P2 в отдельных профилях.
  - У каждого свой ID и права, правильный поставщик; права основного админа не присваиваются автоматически. Проверить доступ к операциям, запрещённым менеджеру.

  </details>

- [ ] **WEB-LOGIN-04 — Запрет входа клиента**

  <details>
  <summary>Подробности проверки</summary>

  - Для обычного клиента выполнить два независимых входа с верным паролем: по клиентскому логину/номеру и по email; затем напрямую отправить те же данные в api/auth.
  - Вход в админку и кабинет поставщика запрещён, пригодный для них токен не выдан. Пользователь не перенаправляется в разрешённый кабинет другого аккаунта.

  </details>

- [ ] **WEB-LOGIN-05 — Запрет входа корпоративного клиента**

  <details>
  <summary>Подробности проверки</summary>

  - Повторить по логину/номеру и email основного корпоративного клиента и его дополнительных пользователей, если они есть, с корректным паролем.
  - Ни административная сессия, ни сессия поставщика не создаются; проверить UI и прямой запрос, несмотря на действующую клиентскую сессию в другом профиле.

  </details>

- [ ] **WEB-LOGIN-06 — Запрет входа перекупщика**

  <details>
  <summary>Подробности проверки</summary>

  - Повторить по логину/номеру и email перекупщика/реселлера, а также его менеджера/подклиента, если доступны.
  - Вход в оба защищаемых контура запрещён. Клиентский токен и правильный клиентский пароль не дают права сотрудника или поставщика.

  </details>

- [ ] **WEB-LOGIN-07 — Коллизии идентификаторов разных типов**

  <details>
  <summary>Подробности проверки</summary>

  - Если тестовый набор позволяет, создать совпадение email либо клиентского логина с email другого типа пользователя; пароли сделать различными.
  - Каждая попытка проверяется с паролем именно целевого аккаунта; сервер не выбирает чужой аккаунт и не смешивает типы. При запрете дублей зафиксировать ограничение вместо создания некорректных данных.

  </details>

- [ ] **WEB-LOGIN-08 — Неизвестный аккаунт и неверный пароль**

  <details>
  <summary>Подробности проверки</summary>

  - Ввести неизвестный email; у существующего сотрудника, админа поставщика и менеджера — неверный пароль, пароль другого пользователя и изменённый регистр пароля.
  - Вход отклонён без выдачи рабочей сессии, отображается понятная ошибка; данные другого пользователя не показываются.

  </details>

- [ ] **WEB-LOGIN-09 — Обязательные поля входа**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить оба пустых поля, только email, только пароль, пробелы в каждом; отправить кнопкой, Enter и прямым запросом.
  - Пустые учётные данные не авторизуют; обязательность проверяется сервером. Если кнопка скрыта, проверить Enter и запрос отдельно, а не считать сценарий закрытым.

  </details>

- [ ] **WEB-LOGIN-10 — Формат и границы email при входе**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить корректный email с поддоменом/плюсом; без @, без домена/точки, с двумя @, пробелами, переводом строки; длины 253/254/255 и длинную вставку.
  - Некорректный адрес не создаёт сессию; ошибки доступны пользователю. Лимит UI 254 проверить отдельно от серверного отказа; не считать ограничение ввода серверной валидацией.

  </details>

- [ ] **WEB-LOGIN-11 — Нормализация идентификатора**

  <details>
  <summary>Подробности проверки</summary>

  - Сравнить email в другом регистре, с крайними пробелами и вставкой; для поставщика и сотрудника попробовать User ID/Name/телефон вместо email.
  - Текущий обработчик ищет email. Поддержку альтернативных логинов, регистра и trim зафиксировать как исследование WEB-Q01; клиентский логин в любом варианте не должен открыть запрещённый кабинет.

  </details>

- [ ] **WEB-LOGIN-12 — Пароль при входе**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить пробелы внутри и по краям, Unicode, спецсимволы, длинный пароль, вставку и автозаполнение; использовать реально заданные тестовые пароли.
  - Пароль маскируется и проверяется без неожиданного обрезания/нормализации. Новые правила создания пароля не должны блокировать вход с действующим старым паролем без согласованной миграции.

  </details>

- [ ] **WEB-LOGIN-13 — Ограничение попыток входа**

  <details>
  <summary>Подробности проверки</summary>

  - На тестовом аккаунте с одного IP выполнить пять неверных попыток, затем шестую, дождаться разрешённого времени и войти правильно.
  - Обработчик содержит порог 5 и окно 120 секунд; проверить фактическую границу, сообщение и обратный отсчёт. После успешного входа счётчик сбрасывается; не блокировать чужие реальные аккаунты.

  </details>

- [ ] **WEB-LOGIN-14 — Повторная отправка входа**

  <details>
  <summary>Подробности проверки</summary>

  - На медленном ответе нажать вход несколько раз и Enter, затем повторить после отказа.
  - Нет нескольких конфликтующих переходов/сессий и входа с устаревшим ответом от предыдущего аккаунта; повтор после исправления доступен.

  </details>

- [ ] **WEB-LOGIN-15 — Ошибки ответа входа**

  <details>
  <summary>Подробности проверки</summary>

  - Воспроизвести 400/401/403/422/429/500, отсутствие сети, HTML вместо JSON, status=false, отсутствие token и некорректный dashboard.
  - Не показывается успешный вход без валидного результата; ошибка видна, загрузка завершается, возможен повтор. Проверить сообщения в message/error/errors и ответ без текста — текущий код может скрывать такую ошибку.

  </details>

## 4. Статусы, удаление и архив

- [ ] **WEB-STATE-01 — Неактивный поставщик**

  <details>
  <summary>Подробности проверки</summary>

  - Для P1 со статусом Не активен войти его админом и двумя менеджерами, включая менеджера с собственной активностью; повторить через прямой api/auth.
  - Новый вход всем запрещён. Собственный активный статус менеджера не обходит статус поставщика; ответ не даёт токен, пригодный к защищённым операциям.

  </details>

- [ ] **WEB-STATE-02 — Заблокированный поставщик**

  <details>
  <summary>Подробности проверки</summary>

  - Повторить все варианты предыдущего пункта для Заблокирован, включая сохранённые правильные пароли.
  - Вход основного админа и всех менеджеров запрещён, другие активные поставщики продолжают работать.

  </details>

- [ ] **WEB-STATE-03 — Индивидуальный статус менеджера**

  <details>
  <summary>Подробности проверки</summary>

  - У активного P1 проверить активного, неактивного, заблокированного и ожидающего активации менеджера по фактически доступным статусам.
  - Запрещённый статус пользователя не даёт сессию; исходный статус поставщика не меняется. Значения и переходы, которых нет в требованиях, согласовать по WEB-Q02/SUP-Q06.

  </details>

- [ ] **WEB-STATE-04 — Удалённый менеджер**

  <details>
  <summary>Подробности проверки</summary>

  - Удалить тестового менеджера, затем войти старыми email и паролем, по сохранённому токену и через ссылку служебного входа.
  - Удалённый пользователь не получает доступ к P1; админ и другой менеджер P1 продолжают работать.

  </details>

- [ ] **WEB-STATE-05 — Архивный поставщик с прежним активным статусом**

  <details>
  <summary>Подробности проверки</summary>

  - Архивировать активного P1; проверить вход его админа и каждого менеджера через форму и запрос.
  - Архив имеет приоритет над сохранённым Активен: вход запрещён всем пользователям, новый рабочий токен не выдаётся.

  </details>

- [ ] **WEB-STATE-06 — Архивный поставщик с запрещающим статусом**

  <details>
  <summary>Подробности проверки</summary>

  - Повторить для поставщиков, архивированных как Не активен и Заблокирован; у менеджеров оставить разные собственные статусы.
  - Оба ограничения действуют независимо; смена собственного статуса менеджера не возвращает доступ архивному поставщику.

  </details>

- [ ] **WEB-STATE-07 — Сессии после смены статуса**

  <details>
  <summary>Подробности проверки</summary>

  - При активном P1 открыть админа и двух менеджеров в отдельных профилях, две вкладки и две сессии одного пользователя; сменить статус на Не активен, затем отдельно Заблокирован.
  - Все ранее открытые сессии P1 теряют возможность читать защищённые данные и выполнять действия; проверить обновление, уже открытую форму и повтор старого запроса. Сессии P2 не затрагиваются.

  </details>

- [ ] **WEB-STATE-08 — Сессии после архивации**

  <details>
  <summary>Подробности проверки</summary>

  - С работающими сессиями админа и менеджеров архивировать P1; проверить открытые кабинеты, прямые URL и повтор API со старыми токенами.
  - Доступ к защищённым операциям прекращён у всех пользователей P1, даже если интерфейс ещё показывает старый экран. Проверить доступ без перезагрузки и после неё.

  </details>

- [ ] **WEB-STATE-09 — Изменение статуса во время входа**

  <details>
  <summary>Подробности проверки</summary>

  - Задержать ответ входа; до его получения заблокировать/архивировать P1 или удалить менеджера. Повторить между выдачей токена и первым запросом профиля.
  - Запоздалый ответ не даёт доступ после запрещающего изменения; окончательную проверку выполняет защищённый серверный запрос.

  </details>

- [ ] **WEB-STATE-10 — Возврат в активный статус**

  <details>
  <summary>Подробности проверки</summary>

  - После Не активен/Заблокирован вернуть неархивного P1 в Активен и выполнить новый вход админом и разрешённым менеджером.
  - Новый разрешённый вход работает; индивидуально запрещённый менеджер не активируется автоматически. Восстановление старых отозванных токенов не считать допустимым без отдельного решения.

  </details>

- [ ] **WEB-STATE-11 — Авторизация после восстановления из архива**

  <details>
  <summary>Подробности проверки</summary>

  - Восстановить P1; записать фактический статус и состав админа/менеджеров. Проверить новый вход каждого разрешённого пользователя.
  - При неактивном/заблокированном статусе вход остаётся запрещён. Состав восстановления и автоматическую активацию исследовать по SUP-Q11; проверить, что удалённый отдельно менеджер не восстановлен случайно и P2 не изменён.

  </details>

- [ ] **WEB-STATE-12 — Смена email и пароля**

  <details>
  <summary>Подробности проверки</summary>

  - Изменить email/пароль админа и менеджера; проверить новый вход со старыми и новыми данными в чистом профиле.
  - Новые сохранённые данные относятся к правильному аккаунту; старый заменённый пароль/логин не подходят. Судьба действующих сессий при смене данных — WEB-Q03.

  </details>

- [ ] **WEB-STATE-13 — Статусы сотрудников админки**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить активного, заблокированного, неактивного, удалённого сотрудника и сотрудника без разрешённых пунктов меню; отдельно супер-админа.
  - Доступ соответствует правам и разрешённому статусу; отсутствующие в требованиях правила для супер-админа и статусной модели согласовать. Зафиксировать любые токены, выданные запрещённым пользователям, даже если UI затем отказывает.

  </details>

- [ ] **WEB-STATE-14 — Просроченная лицензия поставщика**

  <details>
  <summary>Подробности проверки</summary>

  - При активном неархивном P1 и допустимом пользователе проверить вход с истёкшей лицензией и на граничную дату.
  - Лицензия информационная и сама по себе не блокирует авторизацию; архив и запрещающий статус продолжают блокировать.

  </details>

## 5. Сессии, токены и разделение доступа

- [ ] **WEB-SESSION-01 — Прямой доступ без входа**

  <details>
  <summary>Подробности проверки</summary>

  - В чистом профиле открыть защищённые страницы админки/поставщика и запросить их API без токена.
  - Защищённые данные и действия недоступны; редирект не заменяет серверную проверку. После входа открывается только разрешённый контур.

  </details>

- [ ] **WEB-SESSION-02 — Клиентский токен в чужом контуре**

  <details>
  <summary>Подробности проверки</summary>

  - С токенами обычного, корпоративного клиента и перекупщика запросить профиль/операции админки и поставщика; попробовать /oauth/authorize с каждым токеном.
  - Во всех вариантах доступ запрещён; изменить dashboard/scope в URL или браузере недостаточно для получения прав.

  </details>

- [ ] **WEB-SESSION-03 — Токен поставщика в админке**

  <details>
  <summary>Подробности проверки</summary>

  - С токеном админа поставщика и его менеджера открыть административный authorize и защищённый API админки.
  - Права сотрудника не выдаются; данные админки не раскрываются. Права менеджера также не повышаются до админа поставщика изменением запроса.

  </details>

- [ ] **WEB-SESSION-04 — Изоляция поставщиков**

  <details>
  <summary>Подробности проверки</summary>

  - Войти в P1, затем запрашивать записи P2 подменой ID и после выхода войти в P2 в том же браузере.
  - Нет доступа к чужим данным и остатков P1 в таблицах, профиле, кеше или подписках. Проверить служебный вход по токену поверх уже открытой сессии другого пользователя.

  </details>

- [ ] **WEB-SESSION-05 — Недействительный токен**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить пустой, обрезанный, произвольный, истёкший и отозванный token, неверный scope; открыть authorize без token и с сохранённым token.
  - Токен проверяется сервером; авторизация не считается успешной по одному наличию значения. Нет циклов главная—кабинет; неверная сессия очищается.

  </details>

- [ ] **WEB-SESSION-06 — Успешный служебный вход**

  <details>
  <summary>Подробности проверки</summary>

  - Из страницы Поставщики войти за админа P1 и менеджера, проверить профиль и поставщика, обновить кабинет.
  - Открывается именно выбранный пользователь, с его правами; каждый вход отражается в логах согласно SUP-DEF-USER-01. Повторить прямое открытие выданной ссылки.

  </details>

- [ ] **WEB-SESSION-07 — Служебный вход при запрете**

  <details>
  <summary>Подробности проверки</summary>

  - Вызвать служебный вход для заблокированного, неактивного и архивного поставщика и удалённого менеджера.
  - Для архива/удаления доступ не должен возвращаться. Возможность служебного входа при запрещающем статусе отдельно согласуется в SUP-Q06; она не отменяет запрет собственного входа. Проверить права сотрудника на кнопку и запрос.

  </details>

- [ ] **WEB-SESSION-08 — Выход из кабинета**

  <details>
  <summary>Подробности проверки</summary>

  - Выйти штатной кнопкой и через /logout, обновить, нажать Назад, повторить старый защищённый запрос и открыть вторую вкладку.
  - Локальные token/dashboard/scope и данные текущего пользователя очищены, старый отозванный токен не выполняет операции. Поведение других независимых сессий исследовать по WEB-Q03.

  </details>

- [ ] **WEB-SESSION-09 — Выход при недоступном сервере**

  <details>
  <summary>Подробности проверки</summary>

  - Отключить сеть на выходе, затем вернуть сеть и повторить старый запрос.
  - На текущем устройстве кабинет закрыт и данные очищены даже при ошибке; отдельно зафиксировать, остался ли серверный токен рабочим, без заявления об успешном отзыве при неотправленном запросе.

  </details>

- [ ] **WEB-SESSION-10 — Истечение сессии и ошибки профиля**

  <details>
  <summary>Подробности проверки</summary>

  - Во время работы отозвать токен/вернуть 401; отдельно воспроизвести 500 и отсутствие сети у запроса профиля.
  - При 401 защищённый доступ прекращается и сессия очищается; временный сбой не показывает чужую учётную запись. Зафиксировать текущую потерю сессии при любой ошибке getMe как кандидат на дефект.

  </details>

- [ ] **WEB-SESSION-11 — Параллельные вкладки и аккаунты**

  <details>
  <summary>Подробности проверки</summary>

  - Открыть две вкладки, в одной выйти/войти другим пользователем или выполнить служебный вход.
  - Вторая вкладка не выполняет действия от имени неожиданного аккаунта и не показывает смешанные данные; правила одновременных сессий согласовать по WEB-Q03.

  </details>

- [ ] **WEB-SESSION-12 — Безопасность передачи учётных данных**

  <details>
  <summary>Подробности проверки</summary>

  - На тестовом стенде проверить HTTPS, запросы входа/сброса, историю URL после authorize и приглашения, доступные сообщения и консоль.
  - Пароли не передаются в URL и не выводятся открыто. Токены не уходят на произвольный внешний адрес; остаток токена в истории и диагностике зафиксировать отдельно. Не прикладывать реальные секреты к отчёту.

  </details>

## 6. Восстановление и установка пароля

- [ ] **WEB-RESET-01 — Успешная отправка кода**

  <details>
  <summary>Подробности проверки</summary>

  - Для активного админа поставщика и активного менеджера отдельно отправить их email через Forgot password?.
  - Открывается ввод кода с правильным email; письмо поступает только указанному получателю, содержит 4-значный код. Входная сессия ещё не создаётся.

  </details>

- [ ] **WEB-RESET-02 — Email восстановления**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить пустую строку, пробелы, без @/домена, два @, корректный плюс/поддомен, регистр и крайние пробелы, длины 253/254/255.
  - UI и сервер не пропускают некорректные данные; обязательность и максимум 254 в UI проверены. Нормализация email исследуется по WEB-Q01, правильному чужому email не сопоставляется другой аккаунт.

  </details>

- [ ] **WEB-RESET-03 — Неизвестный и неподходящий пользователь**

  <details>
  <summary>Подробности проверки</summary>

  - Отправить email неизвестного пользователя, сотрудника админки, обычного/корпоративного клиента и перекупщика, их менеджеров.
  - Поставщицкий сценарий не выдаёт им код/токен сброса и не меняет пароль; восстановление сотрудника через эту форму не заявлено текущим серверным обработчиком. Проверить фактический отказ и понятность сообщения.

  </details>

- [ ] **WEB-RESET-04 — Восстановление при запрещающем статусе**

  <details>
  <summary>Подробности проверки</summary>

  - Для Не активен/Заблокирован проверить админа и менеджера, отдельно активного менеджера неактивного поставщика.
  - Восстановление не активирует поставщика и не обходит запрет входа. Возможность отправки письма при этих статусах исследовать по WEB-Q04; серверное active() пользователя не доказывает проверку родителя.

  </details>

- [ ] **WEB-RESET-05 — Восстановление архивного аккаунта**

  <details>
  <summary>Подробности проверки</summary>

  - Запросить код админу и менеджерам архивного P1, затем повторить с кодом/токеном, полученным до архивации.
  - Процедура не возвращает доступ архивному поставщику и не восстанавливает его/удалённых пользователей. Допустимость самого изменения пароля без доступа согласовать по WEB-Q04.

  </details>

- [ ] **WEB-RESET-06 — Повторная отправка до таймера**

  <details>
  <summary>Подробности проверки</summary>

  - После успешной отправки нажать Resend до истечения отсчёта; повторить прямой send-code и после обновления страницы.
  - На сервере действует пауза 1 минута для email; UI показывает remaining. Перезагрузка и скрытая кнопка не обходят серверное ограничение; отказ не выдаётся за новое письмо.

  </details>

- [ ] **WEB-RESET-07 — Повторная отправка после таймера**

  <details>
  <summary>Подробности проверки</summary>

  - После разрешённого времени запросить новый код, проверить получателя и новый отсчёт; отдельно воспроизвести отказ повторной отправки.
  - Успех соответствует новому письму; при отказе нет ложного успеха. Текущий UI ставит 60 секунд даже после ошибки — проверить сообщение и возможность повтора; валидность старого кода исследовать отдельно.

  </details>

- [ ] **WEB-RESET-08 — Ввод четырёх символов кода**

  <details>
  <summary>Подробности проверки</summary>

  - Ввести код последовательно, удалять Backspace, перемещаться стрелками, заменить средний символ.
  - Фокус переходит предсказуемо; неполный код не отправляется, заполненный проверяется автоматически. Изменение исправляет ошибку без подстановки чужого email.

  </details>

- [ ] **WEB-RESET-09 — Вставка и недопустимые символы кода**

  <details>
  <summary>Подробности проверки</summary>

  - Вставить 4 цифры, 1/3/5 цифр, код с ведущим нулём, пробелами, буквами, Unicode; повторить ввод с телефона.
  - Корректный код передаётся без потери нуля. Мусор не подтверждает сброс. Обнаруженную обрезку, смешение вставки с прежними символами и принятие букв зафиксировать как дефект/наблюдение, а не требование.

  </details>

- [ ] **WEB-RESET-10 — Неверный и чужой код**

  <details>
  <summary>Подробности проверки</summary>

  - Для email A ввести неверный код и действующий код email B; после ошибки ввести правильный код A.
  - Чужой/неверный код не выдаёт токен; правильный разрешает только сброс A, ошибка исчезает. Нет перехода к новому паролю после отказа.

  </details>

- [ ] **WEB-RESET-11 — Срок действия кода**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить код непосредственно до, на и после двух минут от создания, отдельно после Resend.
  - VerificationCodeManager содержит срок 2 минуты; точную границу сравнения и часы сервера зафиксировать. Отсчёт Resend в 60 секунд не является сроком жизни кода.

  </details>

- [ ] **WEB-RESET-12 — Перебор кода и повтор проверки**

  <details>
  <summary>Подробности проверки</summary>

  - На отдельном тестовом аккаунте проверить серию неверных кодов, повтор уже проверенного кода и две одновременные проверки.
  - Зафиксировать фактическое ограничение попыток и выдачу нескольких токенов; требования к их количеству/отзыву согласовать по WEB-Q05. Не считать наличие rate limit входа защитой проверки кода.

  </details>

- [ ] **WEB-RESET-13 — Связь токена и пользователя**

  <details>
  <summary>Подробности проверки</summary>

  - После верного кода открыть новый пароль; подменить email, token и поля запроса, использовать пустой/случайный/обрезанный токен.
  - Пароль меняется только у аккаунта, которому выдан действительный токен; без подтверждения нельзя сбросить другой аккаунт или повысить его роль.

  </details>

- [ ] **WEB-RESET-14 — Срок и одноразовость токена**

  <details>
  <summary>Подробности проверки</summary>

  - Сбросить пароль по токену и повторить запрос; отдельно проверить токен до и после 60 минут и при выдаче нового токена.
  - Использованный/истёкший токен отклоняется. В config/auth.php срок 60 минут; активную конфигурацию и точную границу сверить на стенде, старые токены после выдачи нового исследовать.

  </details>

- [ ] **WEB-RESET-15 — Минимум и состав нового пароля**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить длины 0/1/5/6/7/8/9, отсутствие заглавной, строчной или цифры, только пробелы; положительно Aa123456 и вариант со спецсимволами.
  - Для обычного сброса сервер требует минимум 8, латинские верхний/нижний регистры и цифры; спецсимвол не обязателен. Проверить отказ через UI, Enter и прямой запрос: схема UI min(6) не должна позволять обход.

  </details>

- [ ] **WEB-RESET-16 — Подтверждение нового пароля**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить пустое подтверждение, несовпадение в одном символе/регистре/крайнем пробеле, совпадение и изменение первого поля после заполнения второго.
  - Отправка возможна только при допустимом совпадении; сервер проверяет password_confirmation. Проверить отсутствие усечения и корректное обновление подсказок.

  </details>

- [ ] **WEB-RESET-17 — Дополнительные границы пароля**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить длинный пароль, Unicode, пробелы внутри, вставку и повтор старого пароля.
  - Не устанавливать отсутствующий максимум и запрет повторения старого пароля; записать фактические ограничения WEB-Q06. Значение не должно незаметно изменяться при отправке.

  </details>

- [ ] **WEB-RESET-18 — Результат успешного сброса**

  <details>
  <summary>Подробности проверки</summary>

  - Завершить обычный сброс и войти новым паролем; попробовать старый пароль.
  - Возврат к форме входа, новый пароль работает только у нужного пользователя, старый заменённый пароль не подходит. Другой менеджер и поставщик сохраняют свои данные; существующие сессии исследовать по WEB-Q03.

  </details>

- [ ] **WEB-RESET-19 — Ошибка сохранения нового пароля**

  <details>
  <summary>Подробности проверки</summary>

  - Воспроизвести неверный/истёкший токен, 422, 500, отсутствие сети, двойное нажатие и Enter во время загрузки.
  - Нет ложного возврата с сообщением успеха; ошибка видна, загрузка завершается, корректный повтор возможен. Неизменённый пароль продолжает действовать; текущая ошибка поля password не должна остаться невидимой.

  </details>

- [ ] **WEB-RESET-20 — Закрытие и обновление процесса**

  <details>
  <summary>Подробности проверки</summary>

  - На каждом шаге закрыть форму/обновить страницу, вернуться назад и начать восстановление для другого email.
  - Нельзя применить код/токен A к B; нет пропуска проверки и бесконечного шага. Сохранение шага и черновика фиксировать как исследование, повторная отправка подчиняется серверному таймеру.

  </details>

- [ ] **WEB-RESET-21 — Приглашение менеджера**

  <details>
  <summary>Подробности проверки</summary>

  - Открыть действительную ссылку с modal=#reset-modal, email и token; задать пароль, повторить испорченную, истёкшую и использованную ссылку.
  - Для разрешённого ожидающего активации менеджера открывается установка пароля; confirm-email и автоматический вход относятся только к нему. Использованная/чужая ссылка не работает; служебные параметры удаляются после завершения/закрытия.

  </details>

- [ ] **WEB-RESET-22 — Приглашение при ограничениях поставщика**

  <details>
  <summary>Подробности проверки</summary>

  - Открыть ранее выданное приглашение после блокировки/деактивации/архивации родителя или удаления менеджера; заменить email другим типом пользователя.
  - Подтверждение не возвращает запрещённый доступ и не меняет чужую роль. Различие требований пароля confirm-email и reset согласовать WEB-Q06; проверить гонку между подтверждением и автоматическим входом.

  </details>

## 7. Заявка «Стать поставщиком»

- [ ] **WEB-REQUEST-01 — Состав формы заявки**

  <details>
  <summary>Подробности проверки</summary>

  - Открыть Get Started и Sign Up.
  - Есть Company Name, Email Address, Phone Number, Which brands do you sell?, How long on the market?, Average quarterly turnover. Отправка — Send a request; это заявка, а не самостоятельное создание активного аккаунта.

  </details>

- [ ] **WEB-REQUEST-02 — Обязательность всех полей**

  <details>
  <summary>Подробности проверки</summary>

  - Оставить форму пустой, затем поочерёдно не заполнить каждое из шести полей; проверить Enter и прямой запрос.
  - Неполная заявка не отправляется; пользователь понимает, чего не хватает. Company Name и Brands из пробелов не считаются заполненными; сервер также отклоняет отсутствующие поля.

  </details>

- [ ] **WEB-REQUEST-03 — Название компании**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить 1/99/100/101 символ, длинную вставку, кириллицу/латиницу/цифры/знаки/эмодзи и HTML-подобный текст.
  - UI ограничен 100; пробельное имя запрещено. На blur крайние пробелы удаляются, повторные пробелы схлопываются; данные в письме совпадают с нормализованным вводом. Текст не исполняется как разметка.

  </details>

- [ ] **WEB-REQUEST-04 — Email заявки**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить корректный email с плюсом/поддоменом, отсутствующий @/домен/точку, два @, пробелы, перевод строки, длины 253/254/255.
  - Некорректный формат отклонён; UI максимум 254, серверные ошибки отображаются. Нормализация/регистр сверяются по WEB-Q01; чужой адрес не подставляется из автозаполнения незаметно.

  </details>

- [ ] **WEB-REQUEST-05 — Телефон заявки**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить пустое значение, международный +971..., цифры, скобки, пробелы/дефисы, буквы, эмодзи, плюс внутри и несколько плюсов, длины 19/20/21.
  - UI сохраняет цифры, скобки и один ведущий плюс и обрезает до 20. Отдельно проверить +, (), +() без цифр: принятие таких значений регэкспом — кандидат на дефект; бизнес-формат и минимальную длину согласовать WEB-Q07.

  </details>

- [ ] **WEB-REQUEST-06 — Бренды заявки**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить 1/99/100/101 символ, только пробелы, список нескольких брендов, перенос строки, Unicode/знаки и длинную вставку.
  - В UI максимум 100, значение обязательно; trim и схлопывание пробелов соответствуют отображаемым данным. Допустимый перечень брендов не придумывается, поле текстовое.

  </details>

- [ ] **WEB-REQUEST-07 — Период работы на рынке**

  <details>
  <summary>Подробности проверки</summary>

  - Раскрыть селект, проверить отсутствие выбора и каждый вариант: Less than 1 year, 1–3 years, 3–5 years, Over 5 years.
  - Выбранная подпись соответствует отправленному market_duration, изменение не сбрасывает остальные поля; проверить клавиатуру и мобильный селект.

  </details>

- [ ] **WEB-REQUEST-08 — Средний квартальный оборот**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить отсутствие выбора и варианты $10M — $50M, $50M — $100M, Over $100M.
  - Выбранная подпись соответствует avg_turnover. Подмена произвольным значением через API не считается допустимой только потому, что сервер проверяет string — WEB-Q07.

  </details>

- [ ] **WEB-REQUEST-09 — Доступность отправки**

  <details>
  <summary>Подробности проверки</summary>

  - Заполнять и очищать поля по одному, выбирать оба селекта; исправлять невалидный email/телефон.
  - Кнопка появляется при заполненных полях и скрывается на время отправки; наличие кнопки не отменяет валидацию. После отказа и исправления отправка снова доступна.

  </details>

- [ ] **WEB-REQUEST-10 — Корректная передача полей**

  <details>
  <summary>Подробности проверки</summary>

  - Отправить тестовую заявку с различимыми значениями и проверить тело запроса.
  - companyName→company, period→market_duration, average→avg_turnover, email/phone/brands передаются своими значениями; поля не переставлены и не теряются.

  </details>

- [ ] **WEB-REQUEST-11 — Успешная отправка заявки**

  <details>
  <summary>Подробности проверки</summary>

  - На стенде с тестовым приёмником почты отправить одну корректную заявку.
  - Появляется Your request has been sent / Our team will contact you shortly. Письмо доходит настроенному получателю заявки; проверить все шесть полей и кодировку, а не только ответ 200. Не отправлять тестовые письма реальным получателям.

  </details>

- [ ] **WEB-REQUEST-12 — Возврат после заявки**

  <details>
  <summary>Подробности проверки</summary>

  - На экране успеха нажать Back to home, затем повторно открыть форму.
  - Окно закрывается, главная доступна, отправка не повторяется сама. Поведение черновика зафиксировать, ошибок прошлой попытки нет.

  </details>

- [ ] **WEB-REQUEST-13 — Отсутствие самостоятельной активации**

  <details>
  <summary>Подробности проверки</summary>

  - После успешной заявки проверить появление аккаунта/токена и попытку входа введённым email.
  - Сама заявка не авторизует и не создаёт активного поставщика: текущий сервер отправляет письмо. Дальнейшая обработка командой находится вне этой формы.

  </details>

- [ ] **WEB-REQUEST-14 — Повторная заявка**

  <details>
  <summary>Подробности проверки</summary>

  - Повторить email существующего поставщика, архивного поставщика, клиента и уже отправленной заявки; проверить двойное нажатие, Enter и повтор после обновления.
  - Не возникает случайного восстановления/изменения чужого аккаунта. Допустимость повторных писем и ограничение частоты согласовать WEB-Q08; дубли от одного действия зафиксировать отдельно.

  </details>

- [ ] **WEB-REQUEST-15 — Серверная валидация заявки**

  <details>
  <summary>Подробности проверки</summary>

  - Напрямую отправить отсутствующие/null/массивы вместо строк, превышение company/email 255 и phone 50, длинные brands/period/average, неизвестные значения селектов.
  - Невалидный тип и обязательность проверяются сервером. UI 100/254/20 отличается от server company/email 255 и phone 50; точные единые пределы и ограничения остальных строк требуют WEB-Q07.

  </details>

- [ ] **WEB-REQUEST-16 — Сбои отправки заявки**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить ошибки email/phone/прочих полей, 422/429/500, недоступную почту и сеть, медленный ответ.
  - Нет ложного успеха, ошибки понятны, значения не теряются незаметно, возможен повтор. Ошибки company/brands/селектов не должны быть невидимыми или автоматически приписываться email.

  </details>

## 8. Общие проверки и устойчивость

- [ ] **WEB-COMMON-01 — Браузеры и мобильные устройства**

  <details>
  <summary>Подробности проверки</summary>

  - Повторить успешный вход каждой разрешённой роли, восстановление и заявку в актуальных Chrome, Safari, Firefox и на iOS/Android.
  - Основные сценарии доступны с мышью/клавиатурой/касанием, нет обрезки ошибок и проблем автозаполнения; версии зафиксированы в отчёте.

  </details>

- [ ] **WEB-COMMON-02 — Обработка всех полей без интерфейса**

  <details>
  <summary>Подробности проверки</summary>

  - Для входа, send-code, check-code, reset, confirm-email и заявки передать пустые/null/неверные типы и дополнительные поля роли/status/gate/id.
  - Сервер не доверяет скрытой кнопке и клиентской схеме; неверный запрос не меняет роль/статус/владельца. Проверить заголовки и границы на тестовых данных без нагрузочного прогона.

  </details>

- [ ] **WEB-COMMON-03 — Безопасное отображение ввода**

  <details>
  <summary>Подробности проверки</summary>

  - В текстовые поля и контролируемые сообщения ошибок передать тестовые HTML/скрипт-подобные строки и кавычки.
  - Интерфейс/письмо отображают безопасный текст, не выполняют код; ошибки не раскрывают пароль, полный токен, трассировку и чужие персональные данные.

  </details>

- [ ] **WEB-COMMON-04 — Недоступность хранилища и сети**

  <details>
  <summary>Подробности проверки</summary>

  - Воспроизвести запрет localStorage, плохую сеть, повторное подключение и смену вкладки во время каждого многошагового сценария.
  - Нет вечной загрузки и ложного успеха; отправка и переходы не выполняются от имени ранее открытого аккаунта. Потерю несохранённого черновика описать фактически.

  </details>

- [ ] **WEB-COMMON-05 — Понятность и доступность ошибок**

  <details>
  <summary>Подробности проверки</summary>

  - Проверить ошибки всех полей, длинные тексты, счётчик ожидания, экранный диктор и фокус после отказа.
  - Пользователь видит причину и может исправить поле; ошибка не сообщается только цветом, не перекрывает действия, не исчезает до возможности прочитать её.

  </details>

- [ ] **WEB-COMMON-06 — Согласованность UI и API**

  <details>
  <summary>Подробности проверки</summary>

  - На каждый запрещающий сценарий сопоставить экран, статус ответа, выдачу токена, запрос профиля и защищённую операцию.
  - Запрет на экране при рабочем токене не считается успешной защитой; каждый обнаруженный разрыв оформляется отдельным дефектом. Успешный ответ без доставки письма не закрывает почтовый сценарий.

  </details>
